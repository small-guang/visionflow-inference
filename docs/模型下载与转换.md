# 模型下载与转换

[返回文档导航](../README.md#文档导航)

从仓库根目录使用 `python -m tools.model_pipeline`：**下载相同源文件 → 用固定配方导出 ONNX → 在目标 GPU 上构建 plan**。只需仓库源码、导出环境和可下载的源文件，无须现存模型文件。工具结构见 [模型维护工具说明](模型维护工具说明.md)。

[catalog.json](../tools/model_pipeline/catalog.json) 是唯一源文件清单：12 份源文件对应 14 个推理模型，固定下载地址、上游版本、大小、SHA256、导出参数和当前 ONNX 摘要。[模型来源与制品身份](模型来源与制品身份.md) 汇总实际模型名称、上游地址和身份核对规则。

## 1. 下载相同的源文件

```powershell
python -m tools.model_pipeline list
python -m tools.model_pipeline acquire --models all --cache artifacts/sources
```

`all` 选择全部 14 个模型，`native` 选择当前采用原生 plan 的 11 个模型。也可指定 `sbs`、`clip_image`、`tbps_clip_text` 等公开别名或内部节点名。工具不自动读取其他项目 `.env`，需要子集时显式使用 `--models`。

`acquire` 依次检查缓存、可选本地源文件、固定上游下载地址，每条路径都必须同时满足大小和 SHA256。本地文件丢失时会自动下载；错误文件不会成为有效缓存。InsightFace 从 `buffalo_l.zip` 提取指定成员，Google Drive 下载会处理公开确认页。

默认缓存目录为 `artifacts/sources/<source_id>/<sha256>/<filename>`，可通过 `--cache` 指定其他位置。相对路径按命令执行目录解析；从仓库根目录运行时，缓存位于仓库下的 `artifacts/sources`。InsightFace 的原始压缩包保存在 `<cache>/archives/<sha256>/<filename>`，提取出的模型仍放入上述按源身份划分的缓存目录。

`tools/models` 是可选本地源文件位置，各模型子目录通过 `.gitkeep` 保留。工具会校验已有源文件并复制到缓存，下载不会自动回填 `tools/models`。也可用 `--source-file SOURCE_ID=PATH` 指定其他位置的本地文件，`--offline` 禁止下载。导出时再次核对身份，因此不会因为文件名或网络地址相同就接受另一份权重。

几个容易被名称误导的来源：

| 当前兼容名称 | 实际源模型 |
| --- | --- |
| `yolov8n_face` | lindevs YOLOv8m-Face |
| `yolo26s_seg` | Ultralytics YOLO26m-Seg |
| `yolo26m_pose` | Ultralytics YOLO26m-Pose |
| `sbs` | FastReID SBS / MSMT17 / 1041 类 |
| `TBPS_clip_*` | OpenAI 基础 CLIP ViT-B/16，未经 TBPS 微调 |

两套 CLIP 各由一份 checkpoint 导出 image/text 两个模型。w600k_r50、106 点和 Face QA 的官方源文件本来就是 ONNX，工具保留现有动态 batch 包装方式。

## 2. 源文件转换为 ONNX

现代导出环境使用 Python 3.13.13；先在独立目录安装固定依赖：

```powershell
py -3.13 -m venv artifacts/env-modern
artifacts/env-modern/Scripts/python.exe -m pip install -r tools/model_pipeline/requirements-modern.txt
artifacts/env-modern/Scripts/python.exe -m pip install --no-deps -r tools/requirements-cn-clip-export.txt
```

Chinese-CLIP 声明的训练数据依赖 `lmdb==1.3.0` 没有 Python 3.13/Windows 的 wheel；导出只使用 `cn_clip.clip`，故单独以 `--no-deps` 安装。完整 Windows 依赖文件摘要另见 [requirements-modern-win.lock](../tools/model_pipeline/requirements-modern-win.lock)。

SBS 需要单独的 Python 3.10 环境，不能直接使用上述新版 PyTorch。Windows 可按完整锁文件安装：

```powershell
py -3.10 -m venv artifacts/env-sbs
artifacts/env-sbs/Scripts/python.exe -m pip install --extra-index-url https://download.pytorch.org/whl/cpu --require-hashes -r tools/model_pipeline/requirements-sbs-win.lock
```

SBS 固定 Python 3.10.11、torch 1.13.1+cpu、FastReID 1.4.0、NumPy 1.24.4、ONNX 1.14.1、ORT 1.16.3。跨平台基础依赖见 [requirements-sbs-export.txt](../tools/requirements-sbs-export.txt)；Windows wheel 哈希锁不能直接用于 Linux。

仅凭下载源文件转换全部模型：

```powershell
python -m tools.model_pipeline onnx --models all --cache artifacts/sources --offline --no-reference --python artifacts/env-modern/Scripts/python.exe --sbs-python artifacts/env-sbs/Scripts/python.exe --output artifacts/onnx-v1 --check-batches 1 4
```

只转换三个 YOLO 时：

```powershell
python -m tools.model_pipeline onnx --models yolov8n_face yolo26m_pose yolo26s_seg --cache artifacts/sources --offline --no-reference --python artifacts/env-modern/Scripts/python.exe --output artifacts/onnx-yolo-v1 --check-batches 1 4 8
```

`--no-reference` 表示不读取旧 ONNX：校验源 SHA256、ONNX checker、输入输出名称/类型/形状以及指定 batch 的 CPU 输出有限性，模型专用导出器原有的 PyTorch/ONNX 检查仍保留。若当前 ONNX 在场，省略该选项会额外做参考数值对照；也可以用 `--reference-root <模型目录>` 指定参考文件。两种模式使用同一个导出配方。

产物在 `<output>/<model>/1/model.onnx`。旁边的 `model.rebuild.json` 自动记录来源、ONNX SHA256、导出参数、运行版本、是否与已知 ONNX 哈希相同及验证结果；无需手工准备此文件，也不再生成独立 `.sha256`。候选文件与 JSON 中的模型、源权重身份和 ONNX 哈希一致后，才一起发布候选目录。未做参考对照时明确记录 `reference_validation: not_requested`、误差为 `null`。导出失败不会发布该模型候选；已经存在的候选不会覆盖。

YOLO 固定 Ultralytics `8.4.61`、动态 batch/空间尺寸、`imgsz=640`、opset 12、`simplify=False`，SBS 显式使用 MSMT17/1041 类。保持导出器原有的输出维度声明；符号维度不改变实际计算，工具通过推理验证实际输出形状。文件版本号、导出时间和维度声明可能使 SHA256 不同，一致性核对以源权重、计算节点、构建参数及推理结果为准。

## 3. ONNX 转为 plan

在目标 GPU 和匹配部署运行库的 TensorRT SDK 环境执行，指定该 SDK 的 `trtexec`。通用候选入口要求显式传入 `--max-batch`，B1/B4 使用以下构建参数：

```powershell
python -m tools.model_pipeline plan --models native --onnx-root artifacts/onnx-v1 --output artifacts/plan-b1-v1 --max-batch 1 --opt-batch 1 --workspace-mib 1024 --trtexec <trtexec完整路径>
python -m tools.model_pipeline plan --models native --onnx-root artifacts/onnx-v1 --output artifacts/plan-b4-v1 --max-batch 4 --opt-batch 1 --workspace-mib 1024 --trtexec <trtexec完整路径>
```

后续需要 batch8 时使用新的输出目录：

```powershell
python -m tools.model_pipeline plan --models native --onnx-root artifacts/onnx-v1 --output artifacts/plan-b8-v1 --max-batch 8 --opt-batch 4 --workspace-mib 1024 --dry-run
```

去掉 `--dry-run`，指定 `--trtexec` 即实际构建。min batch 固定 1，opt 为性能优化的典型批次，max 为允许的最大批次；opt 不能大于 max。输出 `model_bN.plan`、构建参数/哈希记录和日志。构建使用 `--skipInference`，生成 engine 本身不代替推理验证。

Face QA 与 106 点默认 FP32，其余原生模型默认 FP16；文本输入保持 INT64、长度 52/77。固定图像模型只扩大 batch。YOLO 仍为 min `1×3×192×192`、opt `Bopt×3×384×640`、max `Bmax×3×640×640`，覆盖当前七档输入尺寸。

Windows 主机若没有 TensorRT SDK，可在现有 Triton 镜像中运行同一入口。下面以包含 `/usr/src/tensorrt/bin/trtexec` 的 `camtellsvi-tritonserver:latest` 为例；使用前核对镜像的 TensorRT 与目标运行库匹配。等价的 B4 候选构建命令如下：

```powershell
$modelRepoRoot = (Resolve-Path .).Path
$modelPlanOutput = Join-Path $modelRepoRoot 'artifacts/plan-docker-b4-v1'
New-Item -ItemType Directory -Path $modelPlanOutput -ErrorAction Stop | Out-Null
docker run --rm --gpus all --network none --read-only `
  --tmpfs /tmp:rw,size=536870912 -e PYTHONDONTWRITEBYTECODE=1 -e CUDA_CACHE_PATH=/tmp/cuda `
  --mount "type=bind,source=$modelRepoRoot,target=/workspace,readonly" `
  --mount "type=bind,source=$modelPlanOutput,target=/candidate" `
  --workdir /workspace --entrypoint python3 camtellsvi-tritonserver:latest `
  -m tools.model_pipeline plan --models native --onnx-root /workspace/artifacts/onnx-v1 `
  --output /candidate --max-batch 4 --opt-batch 1 --workspace-mib 1024 `
  --trtexec /usr/src/tensorrt/bin/trtexec
```

仓库和候选 ONNX 只读挂载，仅新的 plan 目录可写。命令在独立容器中构建候选，产物由输出目录保留。

`--models all` 也支持为仍使用 ORT 的 AdaFace、OSNet、6DRepNet 生成 plan 候选，这三个模型的 TensorRT 部署须另外验证。扩大 engine 的 batch 不会修改 Triton ensemble、前后处理、`max_batch_size` 或 ALog 请求策略；B1/B8 都是显式候选实验，不是活动部署或回退。当前只把已完成目标设备验证的 B1～4 候选发布为 `model_throughput.plan`，并保留对应 JSON、日志和原始模型别名/来源记录。旧 B1 `model.plan` 可作历史制品保留，不加载，也不通过改名或重新构建改写字节。

直接部署入口 `tools/build_tensorrt_plans.py` 与 `tools/build_yolo_tensorrt_plans.py` 固定产生 `model_throughput.plan`，optimization profile 为 min/opt B1、max B4；其函数 API 和 CLI 都不接受运行配置参数。部署配置直接维护在根 `config.pbtxt`，不需要配置生成步骤。

Jetson 上从相同源文件/ONNX 在目标 JetPack/TensorRT 环境重新构建 plan。本机 RTX 3090 / TensorRT 10.7 的 plan 不能作为 Jetson 通用制品，兼容边界见 [NVIDIA 文档](https://docs.nvidia.com/deeplearning/tensorrt/latest/inference-library/engine-compatibility.html)。

## 4. 维护范围

转换只写独立候选目录，入口拒绝输出到当前 `model_repository`、`tools/models`、`.env` 和 Compose 路径。模型版本升级应增加新的源身份，保留旧 SHA256，不能为了接受新文件而替换旧来源记录。

入口仅提供 `list / audit / acquire / onnx / plan`。`audit` 可额外核对缓存和当前 ONNX；旧 ONNX 已丢失时无需运行它，直接走 `acquire → onnx --no-reference → plan`。
