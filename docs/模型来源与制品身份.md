## 如何确认源文件一致

`acquire` 对本地文件、缓存和下载结果都校验大小与 SHA256，匹配后存入 `artifacts/sources/<source_id>/<sha256>/<filename>`。ONNX 导出前再次校验。源文件身份以 catalog 的摘要为准，文件名、模型别名、下载成功或相同大小都不足以替代哈希校验。

- OpenAI CLIP 使用包含内容摘要的官方 URL；Chinese-CLIP 使用固定提交的下载地址。
- lindevs 和 Ultralytics 使用指定 release；Face QA 使用指定文件提交。
- InsightFace 从指定 `buffalo_l.zip` 提取成员，同时校验包与成员的大小和 SHA256。包摘要及成员路径在 catalog 的 `archive` 中。

catalog 的 `evidence_urls` 保留上游模型映射和来源页面，`publisher_digest` 记录公开摘要及其发布位置。未提供发布方摘要的文件仍有仓库固定 SHA256。发布页和源码提交不保证附件内容永久不变；更换 URL 时须取得同一 SHA256 的文件，模型升级则应新增源身份。

## 转换规则

日常入口为 `python -m tools.model_pipeline`；导出环境安装方法由[转换指南](模型下载与转换.md#2-源文件转换为-onnx)维护。

| 模型 | ONNX 配方 |
| --- | --- |
| Chinese-CLIP、OpenAI CLIP | 各自从固定 checkpoint 导出图像和文本侧，opset 17；保持各模型的归一化方式 |
| SBS | FastReID 1.4.0、PyTorch 1.13.1+cpu、MSMT17/1041 类，opset 17，2048 维归一化输出 |
| 三个 YOLO | Ultralytics 8.4.61、opset 12、`imgsz=640`、动态 batch/空间尺寸、`simplify=False` |
| w600k_r50、106 点、Face QA | 官方源文件已是 ONNX；使用 `tools/dynamic_batch_onnx.py` 包装动态 batch 边界 |

SBS 和 YOLO 保留导出器的输出维度声明，不额外改写符号维度。校验会检查实际推理输出形状，SBS 仍输出 2048 维特征。ONNX 元数据、导出环境和维度声明可能影响文件 SHA256；TensorRT 的构建环境和 tactic 选择也可能影响 plan 字节。模型一致性要求相同源权重、转换配方、计算结果和业务契约，不要求重新导出的 ONNX 或 plan 逐字节相同。

有参考 ONNX 时，工具额外执行数值对照；原文件丢失时使用 `onnx --no-reference`，仍检查源身份、图结构和推理输出。候选需按目标设备和业务样本验证后再部署。

## 制品身份与部署路径

| 阶段 | 身份记录 | 路径 |
| --- | --- | --- |
| 原始 checkpoint / 官方 ONNX | catalog 的大小、SHA256、上游 URL/版本 | `artifacts/sources/<source_id>/<sha256>/<filename>` |
| ONNX 候选 | `model.rebuild.json`：源身份、ONNX SHA256、导出参数、环境和验证结果 | `<output>/<model>/1/model.onnx` |
| plan 候选 | 同名 `.json`：源 ONNX 与 plan 摘要、构建参数、目标环境；另有构建日志 | `<output>/<model>/1/model_bN.plan` |

当前部署 ONNX 的路径、大小和 SHA256 统一由 [catalog.json](../tools/model_pipeline/catalog.json) 的模型条目维护，`audit` 直接按这些记录校验文件。统一转换入口将候选 ONNX 和 `model.rebuild.json` 写入临时目录，检查 JSON 中的模型、源权重身份和候选 ONNX 的实际 SHA256 后，才一起发布候选目录。ONNX 不再生成独立 `.sha256` 文件；Git 中需要保留的空版本目录使用 `.gitkeep`。

TensorRT 节点在 `model_repository/<model>/1/` 保留参考 `model.onnx`，活动运行时只加载 B1～4 `model_throughput.plan`；同名 `.json` 保留构建 provenance。旧 B1 `model.plan` 和旁车可作历史制品保留，但不加载、不作为回退，也不通过改名或重新构建改写其 engine 字节。为保持已有制品可追溯性，活动 plan 旁车中的 `profile: throughput` 字段继续保留；该字段是历史 provenance，不是运行时选择器。

plan 构建精度默认为 Face QA、106 点 FP32，其余原生模型 FP16；FP32 构建禁用 TF32。模型源、精度、shape 范围或目标运行环境变化时需重新构建。Jetson 使用相同源文件或 ONNX，在匹配目标 GPU 和 TensorRT 的环境构建 plan。B8 engine 不会自动改变 Triton 的批量配置，操作见[转换指南](模型下载与转换.md#3-onnx-转为-plan)。
